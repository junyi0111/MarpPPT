# MarpPPT 0.2.0 repair and release plan

## Goal

Repair the publicly reproducible defects found during the anonymous-use check, add automated coverage so CI catches them, resolve production dependency advisories without weakening validation, and publish `0.2.0` only after clean-checkout verification succeeds.

## Acceptance criteria

- Multi-slide PPTX output has no `[Content_Types].xml` Override entries for missing parts, and the renderer's package validator remains strict.
- The package-plugin tests use the same bilingual README files that the published package requires.
- All existing automated tests pass on the declared Node 22 baseline; the build and package validator pass.
- CI executes the automated test suite in addition to build/package validation.
- Production dependency audit has no unresolved high/critical advisory, or any remaining advisory is clearly verified as unreachable/not exploitable and documented before release.
- A fresh anonymous clone can install, build, test, and create/validate the distributable candidate.
- A two-slide build opens in Microsoft PowerPoint without a repair prompt, saves as a new PPTX, closes, and reopens with both slides intact.
- Manifests, package metadata, candidate filename, and release tag consistently identify `0.2.0` / `v0.2.0`.
- Only after all checks pass: commit, push `main`, and push the `v0.2.0` tag.

## Work sequence

1. Reproduce and isolate each reported failure on Node 22. Save a regression test for phantom slide-master Overrides before changing the renderer. Inspect official PptxGenJS status and package advisories.
2. Fix PPTX serialization at the narrowest safe boundary (prefer a validated post-processing correction if upstream remains unfixed); keep strict package-part and relationship checks.
3. Correct the package test fixture to copy both README languages. Re-run the test file to show it passes.
4. Diagnose the remaining worker/integration failures after the PPTX correction; add a targeted regression test for each independent defect and fix the underlying behavior.
5. Resolve dependency audit findings using a supported, compatible dependency update/override or a narrow local patch. Add/update lockfile and test coverage as needed.
6. Add `npm test` to CI, then run the full Node 22 test suite, typecheck/build, package validation, package generation, and production dependency audit.
7. Update all release version references to `0.2.0`; rebuild and validate the package.
8. Verify from a fresh anonymous clone that install, tests, build, package generation, package validation, and audit all pass. Open a multi-slide candidate in PowerPoint, save a copy, close it, and reopen it.
9. Review final diff and git status. Commit the verified release, push `main`, and push `v0.2.0`; report exact validation and release URLs.

## Guardrails

- Do not suppress or loosen the PPTX package validator to make generated files pass.
- Do not use a breaking forced dependency upgrade without confirming compatibility.
- Do not push the version commit/tag until all acceptance criteria pass.
- Preserve the existing README and prior public commits.
