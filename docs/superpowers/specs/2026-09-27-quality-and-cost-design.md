# MarpPPT 製作品質與成本改善規格

日期：2026-09-27。狀態：研發提案，尚未實作或完成新版本驗收。
盤點基準：本機 `main` 的 `3ae3597`；對話中的既有需求與使用者提供的九步製作流程。

## 1. 產品目標與使用者承諾

MarpPPT 的定位是「以成本可控的模板流程，快速把已有資料做成清晰、整齊、可逐項編輯的簡報」。優先服務例行報告、教材、研究摘要及經常改稿的工作。品質應可重複達成，使用者能預測需要多少人工整理。

預設交付包含可編輯 PPTX、內容一致的 Marp 原始檔、必要圖片資源及精簡驗證紀錄。PPTX 的文字、表格、圖表、圖形與連接線保留原生物件；匯入的 PNG/JPEG 是可移動及等比例縮放的圖片，其內部文字不因此成為可編輯文字。

公開範例要由發布套件實際產生，附相同輸入、設定、版本、輸出及檢查範圍。Marp 與 PPTX 目前共享內容計畫，Marp 的部分圖表／示意圖是文字描述；在完成對應渲染器前，只承諾內容對應，不承諾兩者視覺完全一致。

基本品質不因節省用量而降低。省下的工作應來自重複讀取、無目的的重畫和反覆 UI 操作。額外論文查核、外部搜尋與特製視覺，按使用者需求啟用。

## 2. 已確認的缺口與推論邊界

以下是程式與文件盤點；本次沒有重新產生歷史簡報，也沒有對歷史成品逐頁評分。它們能解釋品質風險，不能當成每份成品已出現相同缺陷的證明。

| 觀察 | 證據 | 影響與修正方向 |
| --- | --- | --- |
| 一頁一訊息主要依賴文字指引 | `skills/marp-ppt/SKILL.md`；`src/contracts/presentation-plan.ts` 沒有目的／證據關聯欄位 | 增加簡短編輯提要，讓內容審閱可追查，而非只檢查欄位存在 |
| 正式執行版與多數測試入口不同 | `scripts/apply-presentation-preferences.mjs` 覆寫四個 `dist` 檔；多數 layout／render 測試匯入 `src`；已有一項 built-renderer 封裝測試 | 將覆寫邏輯遷回 TypeScript，直接測試發布 ZIP 內的版面及輸出 |
| 版面對內容特性反應不足 | `blockObjects` 平均分配高度；圖文頁固定分欄；圖片格數依數量；diagram 節點按格子排 | 改為依文字實際高度、圖片比例和關係類型選受控變體 |
| 讀得清楚的下限不一致 | theme 內文 20 pt／下限 18 pt，chart 軸標使用 12 pt | 主內容、軸標、圖例一起納入閱讀檢查 |
| 替代文字只是圖片 ID | `imageObjects` 設定 `alt: assetId` | 增加圖片角色、語意說明、閱讀順序及標題佔位區驗證 |
| 來源引用不能證明結論受支持 | `sourceRefs` 為文字陣列；驗證有引用並不代表引用支持主張 | 綁定來源行範圍、必留事實與主張；語意由審閱確認 |
| 未使用圖片會自動加附圖頁 | `canonicalPlanWithAppendix` 只檢查 60 頁上限 | 明確頁數限制需在規劃時分配附件，不可偷偷增加第 11 頁 |
| `completed` 容易被誤讀 | MCP 依預覽成功判定 completed；`visualQaPassed` 仍為 false；PowerPoint 驗證在 Skill 外部流程 | 保留相容的技術狀態，新增清楚的交付狀態及分項證據 |
| Skill 評估多為規則文字存在測試 | `tests/unit/skill-eval-cases.test.ts` 主要比對 regex | 保留靜態檢查，另用實際模型產物及發布套件輸出做行為驗收 |
| 支援與驗收資訊會過時 | acceptance report 仍記錄未完成宿主交接；其 audit 記錄早於最新成功 Actions | 驗收紀錄綁定提交與環境；不得把 CI 綠燈擴張為所有設備驗證 |

## 3. 必須延續的硬性條件

- 原圖使用 `contain`，只能等比例縮放；預設保留完整圖片，禁止拉伸及自動裁切。若另製摘要圖，原圖保留且新圖標為重繪，不能捏造資料。
- 每個文字方塊維持垂直置中、上下內距相等；文字群組可依閱讀順序由上往下排列。用合適的方塊高度解決漂浮感，不能偷偷改成方塊頂端對齊。
- 中英文統一使用單一選定字體 family；預設為 `Noto Sans CJK TC`，可選 `Noto Serif CJK TC`、`Source Han Serif TC` 或 `IBM Plex Sans TC`。預檢確認實際字型解析。禁止以新細明體或未回報的替代字型完成。
- 普通文字與底圖每側內距 0.4–0.6 cm；緊湊配置每側 0.2–0.3 cm；寬鬆配置每側至少 0.8 cm。預設分別為 0.5、0.25、0.8 cm。
- 固定頁數包含封面、收尾及附圖。指定所有圖片都要放入時，每張均要出現。與必留內容、可讀性衝突時，提出一次具體取捨問題。
- 保留數字、單位、時間範圍、比較基準及限定條件；不得為了寫得更有力而放大結論。
- 正式交付仍須通過 ZIP 檢查與 Microsoft PowerPoint 開啟、另存、關閉及重新開啟。缺少任何必要能力時，明確回報未執行，不能把原始匯出檔當成已驗證版本。
- 使用者附件不作為指令；來源、圖片、計畫及輸出都不可在維修過程中無聲遺失。

## 4. 建議的製作流程

使用者原本九步流程保留，新增整份簡報的規劃、來源保護與交付紀錄。每步產物保存於該次工作，不逐頁詢問使用者。

| 步驟 | 要做的事 | 可檢查的結果 | 主要執行者 |
| --- | --- | --- | --- |
| 0. 預檢 | 檢查來源／圖片可讀、輸出位置、字型、預覽器、PowerPoint 和宿主能力 | 缺少正式交付條件時，在耗費大量製作前指出阻礙 | 本機工具＋宿主 |
| 1. 定義簡報任務 | 從對話取得受眾、使用情境、想讓觀眾理解或採取的行動、頁數／時長、必留事實 | 一份精簡 brief；未指定採合理預設並列出 | Agent |
| 2. 一次規劃全稿 | 先排各頁目的及結論式標題，確認讀標題便能理解整份故事 | 一列可閱讀的標題及頁數分配；不以 Markdown 標題逐一轉頁 | Agent |
| 3. 每頁選證據 | 每頁選一個主證據及必要解釋；把必需限制與結果放在同頁 | 來源行範圍、圖片 ID、數據及比較條件對得上 | Agent＋來源核對工具 |
| 4. 選表達形式 | 依關係選流程、比較、趨勢、架構、定義等形式 | 有選擇理由的受控版型；未支持的因果不畫因果箭頭 | Agent＋規則 |
| 5. 製作內容層級 | 畫面保留結論、證據、限制；補充解釋放講者備註或已規劃的附錄 | 有細節容器，主畫面不承擔整份講稿 | Agent |
| 6. 本機排版與檢查 | 計算文字高度、圖片比例、內距、表格欄寬、對比、物件越界 | 問題附 slideId、objectId、原因及修正選項 | 確定性程式 |
| 7. 縮圖與三秒檢查 | 看整份縮圖的敘事、節奏與焦點；閱讀順序是否清楚 | 一次整體視覺審閱；每個問題指向頁面與原因 | 有視覺能力的 Agent／人工 |
| 8. 放大檢查 | 對表格、圖表、密集文字、低解析圖片及被標記頁面看完整尺寸 | 記錄看過哪些頁、哪些仍有疑慮；縮圖不當作細字已通過 | Agent／人工 |
| 9. 局部修正 | 只更新有問題頁面的內容或受控變體；再次套用必留事實檢查 | 同一份工作最多兩輪針對性修訂；保留未改頁面 | Agent＋本機工具 |
| 10. PowerPoint 驗收 | 最終候選才開啟、另存、關閉、重開，檢查協助工具及閱讀順序 | 綁定最後交付檔案雜湊的紀錄；修正後需更新驗證 | 宿主 CUA／人工 |
| 11. 交付 | 提供 PPTX、Marp、素材包、精簡報告；報告回應使用者最初要求 | 清楚區分已通過、失敗、未執行及仍需實際投影確認 | Agent |

MIT 的指引支持先決定每頁主訊息、再選支持內容並建立視覺層次；這是本流程的內容設計依據。[MIT Slide Design](https://mitcommlab.mit.edu/aeroastro/commkit/slide-design/)

三秒檢查是主觀快速審閱。螢幕縮圖及字級檢查無法證明實際教室後排可讀；正式場地測試需記錄投影設備、觀看距離與人工結果。UGA 也要求確認投影閱讀與物件閱讀順序。[UGA PowerPoint Accessibility](https://uga.teamdynamix.com/TDClient/3190/eitsclientportal/KB/Article/169961/PowerPoint-Accessibility-Best-Practices)

## 5. 內容與版型改善規格

### 5.1 編輯提要

先以新增、可選的 `editorialBrief` 輸入擴充 MCP，維持既有 `PresentationPlan.version: 1` 相容。新 Skill 每次都提供提要；舊客戶端仍能匯出，內容品質狀態為未審閱。欄位定義見實作計畫。

提要不重複整份原文：每頁僅保存一句目的、證據位置、表達關係、主要閱讀焦點、限制與必要備註。頁面主張直接使用計畫中的標題，避免再複製一遍。事實清單只含使用者指定與支持主張的必要項目。

「實驗結果」可以改成「本次設定下延遲下降，但仍須確認正確率」；若來源沒有延遲改善證據，就不得寫出這個標題。定義、方法、議程頁可使用清楚的解釋性標題，不強迫每頁寫成研究結論。

### 5.2 版型選擇

先精修現有一套主題，為既有版型增加有限變體。模型選用途，不提供任意座標。

| 資訊關係 | 首選形式 | 容量起始建議與失敗處理 |
| --- | --- | --- |
| 一個主要指標與條件 | 大數字＋對比基準＋限制 | 一個主要指標、最多兩個輔助數值 |
| 兩方案比較 | 對齊的雙欄或小表格 | 先定相同維度；不對稱段落不要硬排成同高列 |
| 順序／流程 | 水平流程；有分支才用分支圖 | 3–5 個主要節點；更多節點分層或拆頁 |
| 隨時間變化 | 折線圖 | 單位、時間軸與比較條件要明確 |
| 類別數據比較 | 長條圖 | 基線通常從 0 開始；任何例外明示，禁止 3D |
| 定義或方法 | 一句定義＋一個具體例子 | 例子必須有來源或標示為示意 |
| 圖片是主要證據 | 大圖＋簡短解讀 | 圖片占主區，依比例選左右／上下布局；原圖不裁切 |
| 精確數值查閱 | 簡潔表格 | 初始建議最多 5 欄、5 筆正文列；不是 schema 的硬上限，仍按實際高度判定 |

當來源以短句明確表達同一指標由 A 變為 B 時，使用數值對比變體：A 沿用基準內文字級，B 使用 A 的 1.5 倍字級，兩者使用同一字型與單位，中間以方向箭頭連接。長句、條件句、單位不一致或語意不完整時不套用，避免視覺強調掩蓋限定條件。

連續三頁同一版型，或 10 頁簡報超過四頁純條列，先提示審閱，不機械性改版。教學步驟、資料比較等合理連續結構可保留。避免為了達到版型配額而製造裝飾。

### 5.3 字體、留白與圖表

- 投影用途的內文預設由 20 pt 調為 22 pt，標題維持 32 pt／封面 36 pt 起；主文、圖軸、圖例與必要註解不得小於 18 pt。細節擁擠時減少標籤、換形式或調整內容。
- 簡短來源索引可保留 12 pt；觀眾必須理解的限制不得藏在 12 pt 頁腳。完整來源放備註或附錄。12 pt 索引不算「後排可讀」保證。
- 文字框依預估行高設定高度，框內垂直置中；相關文字框組成緊密群組。不要把兩句話平均散在整頁的高度。
- 圖文變體採 `text-left`、`text-right`、`image-above`，依圖的寬高比與可讀性選擇。先精修這三種，避免大量近似模板。
- 裝飾只支持閱讀焦點。不是每段都加卡片或同時用粗體、彩色、邊框；一頁選一個主要證據區。
- 表格內距使用每側命名，避免現有「上下 0.4 cm」被解成合計 0.4 cm。新標準提案：表頭上／下各 0.4 cm；正文四側各 0.5 cm；明確的緊湊表格四側各 0.25 cm。由 P0 範例驗證容量，調整要公開記錄。
- 表頭置中、首欄靠左加粗且保持最寬、數值靠右、敘述靠左、1.2 行高；無法同時滿足時先減少內容或重組表格。禁止用省略號截掉必留數字。
- 圖片分類為品牌、證據、解釋圖。品牌圖不被當成數據證據；圖中文字太小時請求更清晰來源或忠實重繪，原圖仍保留。

對比檢查採普通文字 4.5:1、大字 3:1 的參考門檻，投影內文優先達到 4.5:1。這是採用 W3C 對比方法的產品規則，不代表整份 PPTX 已取得可及性認證。[W3C Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

### 5.4 可及性與可編輯性

為有意義的圖片提供描述其用途的替代文字，標示裝飾元素；使用真正標題佔位區，確認物件閱讀順序。先在既有 PptxGenJS 上做一頁能力驗證，再決定是否需要小範圍 OOXML 支援；不能只在 JSON 寫欄位就宣稱 PowerPoint 已識別。

除執行 Accessibility Checker，還要人工檢查文字順序、顏色是否唯一表意方式，以及圖片描述是否符合用途。Microsoft 建議以標題、版面佔位區、閱讀順序及替代文字維持可及性。[Microsoft PowerPoint Accessibility](https://support.microsoft.com/en-us/accessibility/powerpoint/make-your-powerpoint-presentations-accessible-to-people-with-disabilities)

編輯驗收要實際修改一個標題、一段中文、一個表格儲存格、一個圖表值及一張圖片的大小，另存重開確認，不能只計算 ZIP 裡有幾個文字物件。

## 6. 節省模型與操作成本

預設一個主要 Agent 完成製作；MCP 負責可確定的處理。每頁啟動一名 Agent、每頁重讀整份來源、逐頁生成圖片都不作為預設流程。

普通 10 頁工作的目標為一次整體內容規劃、一次整體視覺審閱；有失敗時最多兩輪局部修訂。這是語意工作階段數，並不保證宿主底層只有相同數目的模型請求。

兩輪修訂是整份工作的共用額度，包含內容溢出與視覺修訂，不能每個錯誤重新取得兩次。相同輸入的執行失敗最多重試一次，由工具回報 attemptCount；工具內部和 Agent 外部不得各自重試而倍增。

| 方法 | 可省的工作 | 保留的品質條件 |
| --- | --- | --- |
| 原文只解析一次，保存來源索引與附件 manifest | 重複讀文件與貼長原文 | 引用、雜湊和必留事實仍可回查 |
| 先分配頁數與內容容量 | 完整匯出後才發現超頁／字太多 | 不縮小字體硬塞，不遺失附件 |
| 字型、尺寸、圖片比例、封裝用本機規則 | 讓模型反覆計算座標與驗證 ZIP | 規則失敗仍阻止正式交付 |
| 一次讀縮圖，完整尺寸只查高風險頁 | 多次上傳整份高解析圖片 | 報告清楚列出放大審閱範圍 |
| 只讓模型修改有問題的頁 | 每輪重新產生全份計畫 | 原來源、完整上下文索引及必留內容仍可取得 |
| PowerPoint 只驗最後候選 | 每次中間改稿都操作桌面 | 最後一版仍須完整開啟／另存／重開 |
| 每次修訂有原因與停止條件 | 無上限嘗試不同模板 | 兩輪後仍失敗回報具體阻礙 |

第一階段仍可重新輸出整份 PPTX；那是本機運算，成本通常不等於再次讓模型規劃全稿。不要先建立昂貴的分頁 ZIP 快取服務。只有量測顯示完整計畫傳輸或預覽重算占主要成本，才另設小型修訂／快取方案；快取必須包含來源、字型、版型及渲染器版本，且不得跨使用者分享附件。

量測每份「通過驗收的簡報」所耗總時間、模型輸入／輸出用量、圖片審閱量、修訂輪數與人工修改頁數，包含失敗重試。宿主未提供 token 或費用資料時標示未知，用可觀測的工具次數和耗時替代，不把訂閱剩餘額度換算成虛構價格。

## 7. 品質門檻與完成狀態

### 7.1 阻擋正式交付的條件

損壞封裝、遺失指定圖片／必留事實、錯誤數字或單位、超出指定頁數、文字裁切、圖片失真、明顯不可讀的主要證據，以及 PowerPoint 重開未通過，均不能由美觀評分抵銷。

完成報告分別記錄 `package`、`layout`、`preview`、`editorial`、`accessibility`、`powerpoint` 的 passed／failed／not_run／partial 狀態、時間、執行方式、artifact SHA-256 和未解決問題。`deliveryState` 為 `draft` 或 `verified`；只有已通過必需關卡的最終檔案可為 verified。部分可及性檢查仍需人工時，必須標出範圍，不使用「完全可及」宣稱。

`verified` 要求上述六項在本產品宣告的檢查範圍內均為 passed，且最終雜湊一致。可及性必需範圍包含標題、替代文字、閱讀順序、對比及 PowerPoint 協助工具檢查；partial 仍是 draft。實際場地投影及特定螢幕閱讀器驗收另行標示，不包含在基礎 passed 的承諾內。

MCP 原 `status` 保留相容語意，新 Skill 對使用者以交付狀態為準。MCP 不自行宣告 PowerPoint 或人工視覺驗證成功。驗證後若檔案被修改，舊報告不能沿用；PowerPoint 另存後也需再檢查最終 ZIP 及關係，核對內容與視覺結果後才能將紀錄綁定最後交付檔。

### 7.2 視覺與內容評分

每項 1–5 分，以有標註的正反例作評分錨點：內容／證據 30%、層次／焦點 25%、可讀性／留白 20%、編輯便利 15%、可及性 10%。發布門檻初定總分 80/100、每項至少 3/5；3 分代表可理解但需少量調整，5 分代表無需整理即可使用。這是專案內部門檻，需以基準樣本校準，不能充作科學保證或全自動美感判定。

## 8. 基準測試、發布與指標

先保存現版本輸出，再用相同輸入、Agent／模型設定與同等工具環境比較。公開基準用合成或可公開的來源；使用者的 DeepSeek 案例可做本機回歸，不直接隨公開測試資料發布。

八組正向案例：例行商業報告、雙語研究摘要、教學定義、線性與分支流程、密集比較表、極端比例／低解析附件、固定 10 頁且每圖必用、長文且有指定必留事實。另設負向案例驗證缺圖、數據矛盾、字型／預覽器缺失、沒有 PowerPoint、頁數無法兼容等行為。

| 指標 | 提案目標 | 量測方式 |
| --- | --- | --- |
| 必留事實及附件保留 | 100% | 基準清單＋語意審閱，來源定位檢查不能替代語意審閱 |
| 正式成品重大缺陷 | 0 | ZIP、版面、PowerPoint、人工檢查 |
| 第一輪達可交付品質 | 至少 7/8 正向案例 | 首次候選通過品質關卡，不計使用者額外改需求 |
| 人工整理 | 每 10 頁不超過 2 頁需要內容／版面修正 | 基準評審記錄，拼字修正與需求變更分開 |
| 模型消耗 | 中位數比基準下降 30% 的研究目標 | 完整工作總用量；資料不足不得宣布達標 |
| 延遲 | 中位數下降，最慢四分位不退步 | 記錄規劃、渲染、視覺審閱、CUA，各階段耗時 |

八組是小型回歸集，報告以 7/8 等實際件數呈現，不能推論所有未知簡報的成功率。模型評估集中在設計里程碑／版本候選，日常 CI 以固定計畫、本機渲染與結構規則為主，控制研發本身的用量。

發布候選的八組正向案例，最終都必須通過硬性關卡；7/8 是首次候選品質目標，不代表允許一份最終成品失敗。負向案例必須正確拒絕或回報阻礙，不列入正向成功率分母。

CI 持續驗證 Linux；macOS 需針對先前程序啟動／逾時失敗定位，完成可重現檢查。發布驗收至少包含新使用者的 Codex 對話啟動、附件交接、產物開啟及 PowerPoint 編輯重開。驗收報告記錄版本與提交，README 的功能與平台宣稱只引用相應證據。

## 9. 實施次序與成本控制

1. **P0：建立可信基準與單一渲染來源。** 保存成品、修正測試與正式套件落差，補上最終交付状态和环境預檢。
2. **P1：改善內容規劃和核心版型。** 加入編輯提要、容量規則、圖表可讀性及有限版型變體；先讓八組範例穩定好看。
3. **P2：建立視覺審閱、可及性和局部修訂閉環。** 保留最終 PowerPoint 關卡，建立可追查報告。
4. **P3：量測與公開發布。** 比較品質及用量，補真實範例與支援矩陣；若省用量未達目標，按量測結果調整。

暫緩大批新主題、自由拖拉編輯器、圖片生成、雲端附件服務及多 Agent／多平台轉接。這些功能要等核心品質與成本指標穩定後另行評估。

每個里程碑指定交付負責人：PM 維護需求及驗收界線，內容設計負責範例與評分，渲染工程負責原生物件與版型，整合工程負責宿主／套件／成本紀錄。小型團隊可由同一人兼任，但發布評審需實際看產物，不能只看模型自己的分數。

具體工程步驟見 [實作計畫](../plans/2026-09-27-quality-and-cost-improvement.md)。
